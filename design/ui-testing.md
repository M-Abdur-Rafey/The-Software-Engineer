# UI testing: design

Status: **draft for review** · 2026-10-13 · Builds on [System Docs](system-docs.md)

## Goal

A manual command, `/software-engineer uitest`, that tests a running app the way users and attackers would.

- **Flows:** logs in as each role and walks every flow.
- **Collaboration:** several users act at once, to check that changes sync.
- **Data consistency:** what the UI shows must match the database.
- **Inputs:** each form gets valid, invalid, random, boundary, unicode and special-character input.
- **Security attacks:** runs a built-in suite against the app.

It plans from System Docs and runs in parallel, cheaply. After a change it tests only what changed and what is linked to it. It never starts without asking.

## Decisions

| Topic | Decision |
|---|---|
| Trigger | Manual only (`/software-engineer uitest [changed\|full] [module...]`). Never part of `orchestrate.js` |
| Confirmation | Always. The skill shows the plan (scope, flows, agents, estimated tokens, target URLs, installs needed) and waits for a yes before launching |
| How users are simulated | **Playwright scripts** generated by small-model agents from System Docs flows. Scripts run in parallel with **zero model tokens**, and are reused across runs and regenerated only for changed flows |
| Services | Reuse running **infrastructure** (DB server, cache, queues). Start the app's own services **fresh on free ports**, pointed at a throwaway test DB. Stop only what this run started |
| Test data | Separate throwaway database (SQLite temp file, or a `<db>_uitest` database on the running server). Dev data is never touched |
| DB consistency checks | Read-only: a SELECT-only helper, or a read-only connection |
| Security tooling | **Built-in payload suites only** (no ZAP/sqlmap installs) |
| Attack targets | **Local dev hosts only** (`localhost`, `127.0.0.1`, `[::1]`, `*.localhost`, `*.test`). Enforced in code. Any other target URL aborts the run; this is not configurable |
| Output | Scripts committed in the project at `tests/ui/`; plan and result summaries at `docs/system/testing/`; raw logs, traces and screenshots git-ignored |
| Scope after a change | Flows of changed modules, plus flows of direct consumers that use a changed touchpoint (from `dependencies.md`). Style- or text-only changes skip testing unless `full` |
| Models | One planner on the host model at low effort. Script generators and failure triage on haiku at low effort. Execution uses no model |
| Ownership | Extends the **testing** agent (`agents/testing/CLAUDE.md` gains a UI-testing section). No new agent |

## Flow

```
skill: uitest
  1. uitest.js scope    -> what to test (or "nothing changed that needs UI tests")
  2. uitest.js env      -> running services/ports, target hosts allowed?, installs needed
  3. show plan, ask the user  ── no ──> stop
                              │ yes
  4. Workflow uitest.js (confirmed: true)
       Environment   start app services on free ports + test DB, seed role users      (haiku)
       Plan          flows in scope -> test matrix: steps, roles, input variants,
                     collaboration scenarios, DB consistency queries, security cases  (host model, low effort)
       Generate      one agent per flow / security suite -> Playwright specs          (haiku, low, parallel)
                     skipped when the flow doc hash is unchanged since last run
       Run           npx playwright test <scoped specs> --workers=N                   (no model)
       Triage        failures only: script error -> one repair + rerun;
                     real bug / security finding -> report entry                      (haiku, low, parallel)
       Report        docs/system/testing/<date>-report.md, state.json
       Teardown      stop what this run started, drop the test DB
```

A workflow can't pause for input, so confirmation happens in the skill before launch. The workflow also refuses to run unless it receives `confirmed: true`.

## Test matrix (planner output, per flow)

- **Roles and steps:** from the flow doc and module README (user → frontend → backend → DB).
- **Input variants for each form field:**
  - valid
  - missing
  - wrong type
  - boundary values (empty, maximum length, maximum length + 1)
  - random
  - unicode and emoji
  - special characters (quotes, `<>&`, backslashes, null bytes)
  - whitespace-only
- **Expected outcomes:** taken from the recorded decisions (answered questions, APIs). If the expected behaviour isn't decided, the case runs as "observed only" and the gap becomes a System Docs question via `sysdocs.js ask`, never a guess.
- **Data consistency:** after each mutating step, a read-only DB query must match what the UI shows (counts, totals, text, analytics).
- **Collaboration:** two or more users in separate browser contexts, running at the same time.
  - user A changes something that user B can see
  - both users edit the same record at once
  - a user loses access while active

  Real-time apps assert that the change arrives within a timeout; others assert it after a refresh.

## Security suites (built-in payloads)

Shipped in `shared/templates/uitest/payloads/`. Each suite runs per changed endpoint or input, except `headers`, which always runs because it's cheap.

| Suite | Checks |
|---|---|
| injection | SQL and NoSQL payloads in every input and query param. Expect no 500s, no SQL error text in responses, no extra rows |
| xss | Reflected and stored payloads in every text field. Fail if any dialog fires or a payload renders unescaped |
| auth | No token; expired, tampered or `alg:none` JWTs; edited role claims; reusing a token after logout |
| access-control | User B requests user A's resources by id on every route; a member calls admin routes (IDOR, privilege escalation) |
| direct-api | Bypass UI validation by calling the API directly with invalid, oversized or extra fields (mass assignment such as `role`, `ownerId`) |
| scraping | Walk sequential ids; enumerate users through error messages; pagination and limit abuse; rate limiting (reported, not failed, in dev) |
| headers | CSP, X-Content-Type-Options, frame-ancestors / X-Frame-Options, Referrer-Policy, Permissions-Policy, CORS policy, cookie flags; no `X-Powered-By` or stack traces |
| data-exposure | No password hashes, tokens or other users' private fields in responses; no secrets in the built frontend bundle |
| csrf | Only when auth uses cookies |

Every security finding gets a severity, a plain-language explanation, a reproduction step and a suggested fix.

## "What changed" (deterministic: `shared/lib/uitest.js scope`)

1. `git diff --name-only <last_tested_commit>..HEAD`, plus uncommitted files. `last_tested_commit` comes from `docs/system/testing/state.json`; if it's missing, the scope is `full`.
2. **Skip rule:** if every changed file is style or text only (`*.css`, `*.scss`, `*.less`, images, fonts, `*.md`, locale/copy files), the result is "no UI test needed" unless `full` was requested.
3. Changed files map to modules through `sysdocs.js impact`. In scope: those modules' flows, plus flows of direct consumers whose `uses` include a touchpoint the changed module provides.
4. Each flow doc's content hash is compared with the one stored in `state.json`. Unchanged flows reuse their existing spec without regeneration, and still run if they're in scope.

## Token budget

- Execution, the bulk of the work, uses no tokens.
- Generation is paid once per flow and repaid only when a flow doc changes.
- The planner reads `INDEX.md`, `dependencies.md` and only the in-scope flow docs.
- Triage runs only on failures, and each failure is triaged once.
- The confirmation step shows an estimate (flows to generate × a per-flow average, measured and stored in `state.json` after each run).

## Build order

1. `uitest.js` CLI (scope, skip rule, host allowlist, state) and its tests
2. Payload suites and fixture templates
3. `uitest.js` workflow plus the skill route with confirmation
4. Validation run on the A/B task tracker (full run, then a changed-only run after the archiving change), measuring tokens and findings

## Parallelism

Playwright workers default to half the CPU cores, capped at 8. Override per run with `uitest --workers N`; the confirmation step shows the number.

## Report entries

Every real bug and security finding in `docs/system/testing/<date>-report.md` has:

| Field | Content |
|---|---|
| What went wrong | Plain language, one or two sentences |
| Intended result | From the flow doc, the recorded decision, or the security rule (with a link) |
| What we got | The actual status, response or UI state, with the request or step that produced it |
| How to fix | The likely cause (file, and function where known) and the change to make |
| Fix command | A ready-to-run `/software-engineer fix: <what>, expected <intended>, got <actual>, in <module>` line, so the fix goes through the normal pipeline with impact checks and a gate |

Script errors that the single repair attempt can't fix are listed separately as "test needs updating", not as app bugs.
